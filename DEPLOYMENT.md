# ShopyGenie Backend — Deployment & Local Development

This covers two things: running the full stack locally with Docker, and
deploying the backend + PostgreSQL to Render for real.

---

## 1. Local development with Docker

### Prerequisites

- Docker Desktop (includes Docker Compose v2) — https://www.docker.com/products/docker-desktop/
- Git
- A copy of both repositories, checked out as **sibling directories** (the
  compose file builds the frontend from `../shopygenie_frontend`):

```
some-folder/
  shopygenie_backend/     <- this repo, docker-compose.yml lives here
  shopygenie_frontend/
```

### Repository setup

```bash
git clone <backend-repo-url> shopygenie_backend
git clone <frontend-repo-url> shopygenie_frontend
cd shopygenie_backend
```

### Environment setup

Copy the example env file and fill in real values:

```bash
cp .env.example .env
```

Required variables (see `.env.example` for the full list with comments):

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | Yes (dev), overridden in Docker | Ignored inside `docker compose` — the compose file points the backend at the `postgres` service directly. Used as-is if you run the backend outside Docker. |
| `JWT_SECRET_KEY` | Yes | 32+ random characters. The app refuses to start in production with a default/short secret. |
| `CORS_ORIGINS` | Yes | Comma-separated. No `*` in production. |
| `PLATFORM_OWNER_EMAIL` / `PLATFORM_OWNER_PASSWORD` / `PLATFORM_OWNER_NAME` | Yes | Bootstraps the initial platform owner account via `scripts/seed.py`. Equivalent to what other docs call `INITIAL_PLATFORM_OWNER_EMAIL`/`PASSWORD`. |
| `SMSGATE_BASE_URL` / `SMSGATE_USERNAME` / `SMSGATE_PASSWORD` / `SMSGATE_DEVICE_ID` | No | Local-dev/seed convenience only — applied to the demo tenant by `scripts/seed.py`, never read by the live send path. Leave blank to use the console-logging SMS stub. Real tenants configure their own SMSGate account in Settings → Notifications. |
| `UPLOADS_DIR` / `MAX_UPLOAD_BYTES` | No | Defaults are fine (`uploads`, 5MB). |
| `ENVIRONMENT` | No | `development` locally; set to `production` only for a real deployment. |

Never commit `.env` — it's gitignored. `.env.example` has placeholders only.

### Starting the platform

```bash
docker compose up --build
```

This builds and starts three services:

- `postgres` — PostgreSQL 16, with a health check gating the backend's startup
- `backend` — waits for Postgres to actually accept connections, runs
  `alembic upgrade head`, seeds permissions/roles/the platform owner
  (idempotent — safe to run every start), then serves the API on
  `http://localhost:8080`
- `frontend` — nginx serving the built Angular app on `http://localhost:4200`,
  with SPA fallback routing configured so deep links survive a refresh

### Running in the background

```bash
docker compose up -d --build
```

### Viewing logs

```bash
docker compose logs -f            # everything
docker compose logs -f backend
docker compose logs -f frontend
docker compose logs -f postgres
```

### Stopping

```bash
docker compose down
```

This stops and removes the containers but **keeps** the named volumes
(`pgdata`, `backend_uploads`) — your data survives.

### Resetting local data (destructive)

```bash
docker compose down -v
```

`-v` deletes the named volumes too — **this permanently deletes your local
database and uploaded files.** Only do this when you actually want a clean
slate. There is no undo.

### Database migrations

Migrations run automatically on every backend container start
(`docker-entrypoint.sh`). To manage them manually:

```bash
# Enter the running backend container
docker compose exec backend sh

# Inside the container:
alembic upgrade head          # apply all pending migrations
alembic current               # check current revision
alembic history                # list all migrations
alembic downgrade -1           # roll back one migration (use with care)

# Create a new migration after changing a model, from your host machine
# (with the local venv active) or inside the container:
alembic revision --autogenerate -m "describe the change"
```

Always read an autogenerated migration before applying it — Alembic is good
but not infallible, especially around renamed columns.

### Backend development inside Docker

```bash
docker compose exec backend sh          # shell into the running container
docker compose exec backend pytest -q   # run the test suite
docker compose exec backend alembic upgrade head
```

For active development, most people run the backend natively (own venv,
`uvicorn app.main:app --reload`) against the Dockerized Postgres only —
faster iteration, same database. That's exactly what this project's own
development has used throughout.

### PostgreSQL connection details

| | |
|---|---|
| Host (from your machine) | `localhost` |
| Port (from your machine) | `5433` (mapped from the container's `5432`, chosen to avoid clashing with a local Postgres install) |
| Host (from another container) | `postgres` |
| Database | `shopygenie` |
| User / Password | `shopygenie` / `shopygenie` (local dev only — never use these in production) |
| Volume | `pgdata` (persists across `down`, wiped by `down -v`) |

### Health checks

```bash
curl http://localhost:8080/health      # backend
curl http://localhost:4200/            # frontend (200 = serving)
docker compose ps                      # shows health status for all services
```

### Debugging common problems

| Symptom | Likely cause / fix |
|---|---|
| `port is already allocated` | Something else is using 8080/4200/5433. Stop it, or change the left-hand port in `docker-compose.yml` (e.g. `"8081:8000"`). |
| Backend keeps restarting, logs show connection refused | Postgres isn't healthy yet — check `docker compose logs postgres`. The backend's `depends_on: condition: service_healthy` should prevent this, but a very slow first-boot disk can still race; just wait or re-run `docker compose up`. |
| `alembic upgrade head` fails on startup | Check `docker compose logs backend` for the actual migration error. Often a migration file was hand-edited incorrectly, or the DB is from an incompatible earlier version — see the reset section above. |
| Frontend loads but every API call fails / CORS error | `CORS_ORIGINS` in `.env` doesn't include the frontend's origin. For the Docker setup that's `http://localhost:4200`. |
| Frontend shows a blank page after `docker compose down -v` then `up` | Expected — this is a real reset. Log in with `PLATFORM_OWNER_EMAIL`/`PASSWORD` from `.env`. |
| Changes to backend code aren't showing up | You need `docker compose up --build` (or `docker compose build backend`) — the image is only rebuilt when asked, unlike a bind-mounted dev setup. |
| Build seems to reuse stale, broken layers | `docker compose build --no-cache backend` (or `frontend`). Slower, but guarantees a clean rebuild. Only needed if you suspect layer caching hid a real change (e.g. `requirements.txt` edited but pip install didn't rerun) — not needed for ordinary code changes. |
| `401`/`403` immediately after fresh seed | Make sure `PLATFORM_OWNER_EMAIL` and `PLATFORM_OWNER_PASSWORD` in `.env` match what you're typing into the login form — the seed script only creates the account once; changing `.env` afterward doesn't retroactively change the password. |

## 2. Production deployment — Render (backend + PostgreSQL)

Target architecture:

```
Netlify (frontend, static)
        |
        v
Render Web Service (this backend, FastAPI + Uvicorn)
        |
        v
Render PostgreSQL (managed)
```

### 2.1 Provision PostgreSQL on Render

1. Render dashboard → **New** → **PostgreSQL**.
2. Pick a name, region, and plan. Region should match the backend service's
   region to keep latency down.
3. Once created, Render shows both an **Internal Database URL** and an
   **External Database URL**. Use the **Internal** one for `DATABASE_URL` on
   the backend service (same-region traffic, no public exposure needed) —
   only use the external URL for one-off local admin access (e.g. `psql`).
4. Render's connection string uses `postgresql://...` — this backend needs
   the async driver, so change the scheme to `postgresql+asyncpg://...`
   before setting it as `DATABASE_URL`.
5. Backups/retention: configured per the Render Postgres plan you choose
   (paid plans include automated daily backups with a retention window —
   check Render's current plan page, this varies and isn't something to
   hard-code here).

### 2.2 Create the backend web service

1. Render dashboard → **New** → **Web Service** → connect the
   `shopygenie_backend` Git repository.
2. **Build command:**
   ```
   pip install -r requirements.txt
   ```
3. **Start command** — run migrations then start Uvicorn with a real
   production ASGI setup (not `--reload`, and bind to Render's `$PORT`):
   ```
   alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port $PORT
   ```
   (Alternative: Docker deploy — point Render at this repo's `Dockerfile`
   instead of a native build; `docker-entrypoint.sh` already does the
   migrate-then-serve sequence. Either approach is valid; native build/start
   commands are simpler to iterate on from the Render dashboard.)
4. **Health check path:** `/health`.
5. Set environment variables (see table below).
6. Deploy. Watch the deploy log — migration failures show up here.
7. Verify: `curl https://<your-service>.onrender.com/health` → `{"status":"ok"}`.

### 2.3 Environment variables on Render

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | **Required** | Internal Render Postgres URL, scheme changed to `postgresql+asyncpg://`. |
| `JWT_SECRET_KEY` | **Required** | Generate a real random 32+ character value (e.g. `python -c "import secrets; print(secrets.token_urlsafe(48))"`). The app refuses to boot without one in production. |
| `ENVIRONMENT` | **Required** | Set to `production` — this activates the startup guard against weak secrets and wildcard CORS. |
| `CORS_ORIGINS` | **Required** | Your Netlify frontend's real URL(s), comma-separated. No `*`. |
| `PLATFORM_OWNER_EMAIL` / `PLATFORM_OWNER_PASSWORD` / `PLATFORM_OWNER_NAME` | **Required** (first deploy) | Used once by `scripts/seed.py` to bootstrap the initial platform owner. Use a real, strong password — set via Render's dashboard, never in Git. |
| `SMSGATE_BASE_URL` / `SMSGATE_USERNAME` / `SMSGATE_PASSWORD` / `SMSGATE_DEVICE_ID` | Optional | Applied only to the seeded demo tenant if set; not read by the live per-tenant send path. Real tenants configure their own SMSGate account in Settings → Notifications. |
| `UPLOADS_DIR` | Optional | Defaults to `uploads`. **Note:** Render's filesystem is ephemeral on redeploy — for durable expense-evidence storage in production, mount a Render Disk at this path, or migrate to object storage later. Not wired to S3/etc. in this codebase yet. |
| `MAX_UPLOAD_BYTES` | Optional | Defaults to 5MB. |
| `ACCESS_TOKEN_EXPIRE_MINUTES` / `REFRESH_TOKEN_EXPIRE_DAYS` | Optional | Sensible defaults already set. |

Never put real values for any of these in Git. `.env.example` documents the
same list with placeholders only.

### 2.4 Migrations in production

Every deploy runs `alembic upgrade head` before the new backend version
starts serving traffic (see the start command above, or the Docker
entrypoint). This is deliberate:

- Deploy → Postgres reachable → `alembic upgrade head` → backend starts → health check passes → Render routes traffic to the new instance.
- If a migration fails, the deploy fails and the previous instance keeps
  serving — never a partially-migrated database silently live.
- Nothing here ever runs `alembic downgrade` automatically. Rolling back a
  bad migration is a deliberate, manual `alembic downgrade -1` against the
  Render database (via the external connection URL), done with the same
  care as any other production database change.

## 3. `render.yaml` (infrastructure-as-code, optional)

`render.yaml` in this repo describes the backend service + a managed
Postgres database for Render's Blueprint deploys. It defines which
environment variables exist but never their values — Render prompts for
secret values (`sync: false` entries) at blueprint-apply time; nothing
sensitive is committed. Using it is optional — everything in section 2
above works equally well clicking through the Render dashboard directly.
